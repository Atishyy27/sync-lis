## Who the user is

Two kinds of people reach the product. The host already likes the idea and starts a room. The friend is invited by link, usually has no extension, and is the highest-intent visitor the product will get (comment in `worker/src/SyncRelay.js`, roomLinkResponse). The goal is the first 1,000 users and their reports (`LAUNCH.md`).

## The top 3 changes

### 1. Hold an empty room for 10 minutes (F1)
Change: when the last member leaves, the relay freezes the transport, clears the host, stamps `emptyAt`, and sets a Durable Object alarm. `alarm()` deletes rooms empty for 10 minutes or more. A join to a held room clears the stamp; the first joiner becomes host. The invite page for a held room says nobody is in it right now instead of "live".
Expected effect: a blip or a slow-installing friend no longer kills the room. Cost: room state (title, URL, last 80 chat lines) sits in the relay's storage 10 minutes longer, so `extension/PRIVACY.md` gets one sentence. The 10 minutes is my choice, not a measured value; Socket.IO's own example for the same pattern uses 2 minutes (below), the friend-installing case needs longer.
Check: `test/unit/relay.test.js`: rejoin within the window works, host is reassigned, transport is frozen, after 10 minutes the alarm deletes it and `/r/<code>` says not live, a room with people in it is never deleted.

### 2. Keep trying to get back, and say so (F2)
Change: rejoin loop with growing waits (1.5, 3, 5, 8, 12, 20, 30, 30 s, about 110 s in total), stops at once if the relay answers "No session with that code" (the room is really gone), if the user leaves, or if the tab closes. Posts a note to the panel ("Connection lost, reconnecting") and one on success, using the existing `note` message, no new UI.
Expected effect: wifi switch, sleep and wake and short outages stop ending rooms. Check: `test/unit/sw-reconnect.test.js`: network down for 3 s then back, session survives; relay answers room gone, ends at once; user leaves mid-retry, no more attempts; ends after the last attempt.

### 3. The room-link path (F3 and F4, one user story: "my friend clicks the link")
Two commits.
(a) `01b794b`, the install join: reused from his own commit e19d5ba (on `fix/mehfil-guest-friction`, not merged to master), cherry-picked with `-x`. On install the service worker injects `joinlink.js` into open tabs shaped like a room link, so the invite tab joins itself. It runs on every `onInstalled` reason, which is harmless because `joinTabOnce` ignores a repeat for the same room.
(b) `5c69c35`, the link match: a page counts as a room link only if it is on the default relay origin, or carries `<meta name="sync-lis-room" content="CODE">` (the relay's invite page and the Node server's get it). That keeps self-hosting and stops `reddit.com/r/funny` from opening a connection or closing your room. `joinlink.js` is wrapped in a function so a second injection cannot throw.
Expected effect: no stray connections to unrelated sites; the friend's install-to-joined step loses a click (the click part is not proven, see below). Check: `test/unit/roomlink.test.mjs` (11 tests, 5 red on the old code) and in real Chromium `test/ci/e2e.mjs` (reddit-shaped page opens no connection, a friend's tab joins from the relay's invite page).

## Shipped references for the same patterns (read 25 Nov 2026)

1. Cloudflare Durable Objects, "Durable Object Time To Live" example (`developers.cloudflare.com/durable-objects/examples/durable-object-ttl/`): the documented way to expire state is `setAlarm` plus `alarm()`. Warns against extending the alarm in the constructor, because the constructor runs before the alarm handler on wake. We take: set the alarm only on the empty transition, never in the constructor.
2. Cloudflare alarms docs (`.../durable-objects/api/alarms/`): one alarm per object, "store your event schedule in storage and have `alarm()` process due events, then reschedule". We take: one alarm for all empty rooms, scan with `storage.list`.
3. Socket.IO "Connection state recovery" (`socket.io/docs/v4/connection-state-recovery`): a shipped real-time library keeps a dropped client's session for a finite window; its example is `maxDisconnectionDuration: 2 * 60 * 1000`, and it says recovery "will not always be successful" so the app must handle the miss. We take: a finite hold, and a clean "room is gone" path.
4. Chrome extension service worker lifecycle (`developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle`): 30 s idle limit; socket traffic resets it (Chrome 116); globals are lost on shutdown. We take: the existing 20 s ping is right; in-memory sessions are a known limit (F6, not built).
5. Chrome `runtime.onInstalled` (`developer.chrome.com/docs/extensions/reference/api/runtime`): reasons `install`, `update`, `chrome_update`. We take: act only on `install`. The page does not say anything about content scripts and open tabs; that content scripts are not injected into already-open tabs is from the Chrome content-script model as I know it, and the unit test cannot prove it. The Playwright run cannot prove it either (it loads the extension before any page opens).

An AWS "exponential backoff and jitter" page was fetched but came back empty; the waits in change 2 are a plain ladder, no jitter, because one client per room makes a thundering herd unlikely. That is a judgement, not a measurement.

## Not built, ideas for later

## Merge cards

Change 1, `da0a4af` (+ PRIVACY.md sentence):
- What: the relay keeps a room 10 minutes after its last member leaves, then deletes it.
- Why: a host alone (waiting for a friend to install) or a wifi blip used to delete the room.
- Risk: room title, URL and the last 80 chat lines sit in the relay's storage 10 minutes longer; `extension/PRIVACY.md` now says so, so the privacy policy the store links to may need republishing. The worker needs your manual deploy. The 10 minutes is my choice, not measured. The Node `server.js` relay is unchanged.
- Roll back: `git revert da0a4af`, redeploy the worker. Rooms are then deleted at once again; any rooms already held just expire with the old code's next close.

Change 2, `81b103e`:
- What: after a drop the extension retries about 110 seconds (1.5, 3, 5, 8, 12, 20, 30, 30 s), says so in the panel, stops at once if the room is gone or you leave. Joins time out after 10 seconds. The panel's Leave works while reconnecting.
- Why: it used to give up after one failed try 1.5 seconds after the drop.
- Risk: while reconnecting it pings an extension API every 20 s so Chrome does not stop the service worker (a review finding: the 30 s idle limit would otherwise end the session around 30 s in); a 10 second connect timeout also applies to first-time joins on a very slow network. It ships in the extension, so it needs a store upload (version bump) which this branch does not do.
- Roll back: `git revert 98d1544 81b103e`.

Change 3, `01b794b` and `5c69c35`:
- What: the install join (his commit) and room-link detection that needs the default relay or the page marker.
- Why: reddit-shaped pages opened connections and could drop a room; invite tabs open during install never joined.
- Risk: a self-hosted relay is recognised only by the `sync-lis-room` marker on its invite page, so a self-hosted relay on old code (no marker) stops auto-joining from links until it is updated; the Node `server.js` in this branch has it. The deployed default relay is allowed by name, so it does not need the marker first. The install join is not proven in a browser.
- Roll back: `git revert 5c69c35 01b794b`.

## Review rounds

Round 1 (one Sonnet code-reviewer over the whole production diff): two findings, both fixed with tests that fail on the previous code. (1) The 110 s retry ladder outlasts Chrome's 30 s service-worker idle limit, because the 20 s ping stops with the socket: now an extension API is called every 20 s while reconnecting. (2) A rejoin whose agent injection failed left the panel stuck on "reconnecting": now the panel is told the room ended. The reviewer found no problem in the relay's alarm logic, the leave and two-session races, the invite page escaping, or self-hosted relays.
